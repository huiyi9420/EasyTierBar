# EasyTierBar 开发日志 — 状态健康检测与恢复

**日期**: 2026-08-13
**主题**: 从「进程在就显示运行中」到「真实网络健康 + 可恢复 + 可配置省电」

---

## 背景

v2 重构（见 `dev-log-2026-08-12.md`）上线后，暴露出一个真实场景的问题：

用户挂机一晚，第二天发现：
- 穿透不了公司网络
- Web 控制台看不到「赵路路」这台机器（配置中心 session 已断）
- **但 app 仍显示「运行中」**（绿色）
- 没有自动重连，也没有刷新/重连按钮可操作

诊断后发现实际是「**配置中心断开、P2P 残留还活着**」的尴尬状态：
- core 进程在跑、RPC 可达、peer 列表非空 → app 按 v2 逻辑判定 running
- 但配置中心 session 早已断了（Web 控制台看不到这台机器）
- 与对端的隧道是昨晚协商的残留连接，碰巧还能转发，所以 xt 暂时通

## 三个根因

1. **状态检测太弱**：`checkStatus` 只跑 `easytier-cli node info`（RPC 可达 = running），完全不反映网络层健康。
2. **没有定时刷新**：状态只在打开菜单时（`menuWillOpen`）检测一次。挂机一晚不打开菜单，状态冻结在昨晚的 running。
3. **没有恢复手段**：断了之后，用户只能「卸载守护进程」再「安装」（弹两次密码、删配置），太重。

## 本次完成的工作

### 1. 四态健康状态（`ServiceManager.DaemonStatus`）

```
case notInstalled           // plist 不存在 → 灰
case installedNotReachable  // RPC 不通 → 黄
case noNetwork              // RPC 通但无对端 peer → 橙（新增）
case running                // RPC 通 + 有对端 peer → 绿
```

`checkStatus` 在 RPC 可达后，额外跑 `peer list`：peer 数 ≤ 1（只有本机）= `noNetwork`。这样「core 活着但网络层没连上」能被识别为橙色，而非误报绿色。

### 2. 定时自动刷新（可配置间隔）

- app 启动后开 Timer，周期性 `checkStatus`，不再依赖打开菜单
- 默认 5 分钟（从初版的 60 秒放宽——每次检测起 2 个 `easytier-cli` 子进程，60 秒太频繁、费电）
- 新增「自动检测间隔」子菜单：**关闭 / 1 分钟 / 5 分钟 / 15 分钟**，切换即时重建 Timer
- 间隔存 UserDefaults（`statusIntervalSeconds`），持久化

### 3. 重启守护进程（恢复手段）

- `ServiceManager.restartDaemon()`：`launchctl kickstart -k system/com.easytier.core`（AppleScript sudo，弹一次密码）
- **保留配置**（不删 plist、不清 config-dir），只重启 core 进程，让它重新连配置中心、重新协商 peer
- 比「卸载 + 重装」轻量得多（不丢配置、不重输地址）
- 用于：配置中心 session 失联、网络卡死、死链残留等

### 4. 「刷新状态」菜单项

无密码，立即 `checkStatus + updatePeerList`。不想等定时刷新时可手动触发。

## 关键技术决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 健康判定 | RPC + peer 双重 | 单看 RPC 会误报「进程活着但网络断了」 |
| 默认刷新间隔 | 5 分钟 | 60 秒太频繁（CPU 频繁唤醒阻止深度睡眠）；5 分钟一天 288 次，平衡及时性与电池 |
| 间隔可配置 | 四档子菜单 | 不同用户对「及时性 vs 省电」权衡不同；关闭选项给最大化省电 |
| 恢复方式 | `launchctl kickstart -k` | 比 unload/load 轻（保留配置）；比 pkill 标准（launchd 原子重启） |

## 一个重要修正

初版诊断时，我看到「公司内网入口节点 peer `rx/tx = 0 B`」就判断它是死链、xt 应该不通。**这个判断错了**——实测 `xt.seeyon.com` 返回 302（通的）。

根因：peer 列表的 `rx/tx` 统计的是 **peer 隧道直接流量**，而到公司内网（172.20.2.0/24）的数据走的是**子网代理转发 + 经中继节点转发**，这部分流量不计入该 peer 的 rx/tx。**不能凭 peer 的 0 流量判定死链**。

因此四态检测用的是「peer 数量」（结构性指标），而非「peer 流量」（会误导）。

## 已知局限

**死链残留**：某台对端实际已断开、零流量，却仍残留在 peer 列表里，导致 peer 数 > 1，状态仍是绿色（running）。这种情况：
- 去 Web 控制台确认这台机器是否还在设备列表（配置中心 session 是否断）
- 用「重启守护进程」强制 core 重新协商

要完美识别死链需要解析每个 peer 的实时流量 + 心跳新鲜度，复杂度高，暂不做。「重启守护进程」是当前的有效兜底。
